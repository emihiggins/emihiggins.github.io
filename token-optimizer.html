Claude Code Token Optimizer

A VS Code extension that reads local Claude Code session transcripts and recommends concrete, dollar-quantified ways to reduce token spend — entirely on-device.

Install from Marketplace ↗ Source on GitHub ↗ ← Back to portfolio

The problem

Coding agents like Claude Code are powerful but expensive, and the cost signals are diffuse — a single session might spend $15 without any obvious moment where "that read was wasteful" or "that search should have been scoped." Claude Code writes every turn to a local JSONL transcript (~/.claude/projects/), including full usage metadata — input tokens, output tokens, cache reads/writes, tool calls, compactions — but doesn't surface any of it. I wanted a tool that answers: where is the money going, and what specifically should I do differently?

The approach

The pipeline

A purely-local analyzer, end to end:

  1. Discover every transcript under the local Claude home.
  2. Stream & parse each JSONL file into a typed session model, folding usage / tool / compaction events as it goes.
  3. Run a rules engine — ten independent detectors, each keyed to a specific transcript pattern with an explicit token/cost estimate.
  4. Aggregate findings into recoverable-dollar totals by category, rank the most common mistakes, and split "one-off fixes" from "habits."
  5. Track a daily efficiency series (cache-reuse %, cost/day, compactions) persisted to storage so history survives transcript pruning — a regression banner fires only when both 7-day windows have enough data.
  6. Drill into any expensive session: a tokens-per-turn chart with compaction points marked, plus the priciest tool calls with their exact target.

The ten detectors

  • Context compactions (each drops thousands of tokens and re-primes a cold cache)
  • Context-pressure warnings before an auto-compaction
  • Broad or unscoped grep/rg/find searches
  • Uncapped cat/git diff/git log output dumps
  • Oversized or repeated reads of the same file
  • Reading a file back immediately after writing it
  • Redundant read-only inspection commands
  • Failed/interrupted tool calls whose output was billed and discarded
  • Low cache reuse (a signature of volatile prompt prefixes)
  • High-input / low-output round-trips

Engineering decisions I'm proud of

  • Data layer has no vscode dependencyThe parser, model, pricing, rules, and aggregation are pure TypeScript, unit-tested against fixtures and a temp ~/.claude tree — keeping tests fast and the extension shell thin.
  • Honest cost estimatesClaude Code's local stats report costUSD: 0, so I built an editable rate table (Opus/Sonnet/Haiku input/output, plus cache-read at 0.1× and cache-write at 1.25–2×). Every recommendation carries a dollar figure — and the README is explicit that on an already-efficient setup recoverable waste can legitimately be small. I didn't inflate the numbers.
  • Rules are one-file-each and independently testableAdding a new detection is dropping a file in src/rules/ — nothing else changes.
  • Regression alerts resist noiseThe trend logic requires ≥3 active sessions and ≥20k tokens per window before firing, because false alarms on sparse history are worse than missed ones.
  • Fully local, fully privateNo telemetry, no external calls. Everything runs on the machine that already has the transcripts.
